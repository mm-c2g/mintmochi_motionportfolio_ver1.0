# 01. タイポグラフィ

このサイト専用の規則。一般的なベストプラクティスの列挙ではなく、**このサイトで実際に使う値**を決める。
根拠は `research/data/reference-sites.json`（参考6サイトのCSS実測値）と
`research/data/design-systems/*.txt`（公開デザインシステムの本文）。
すべて数値の裏付けがあるものだけを採用する。分からないものは「確認できず」と明記する。

---

## 1. 使用フォント（現状維持）

- 欧文: **Inter**（200 / 300 / 400 / 500 / 700 を読み込み済み）
- 和文: **Zen Kaku Gothic New**（300 / 400 / 500 を読み込み済み）
- 指定順: `'Inter', 'Zen Kaku Gothic New', sans-serif`（`style.css` 46-48行目、変更なし）

この2書体そのものは6参考サイトのどれとも一致しない（後述の通り、参考6サイトは
Barlow / neue-haas-unica / aktiv-grotesk+termina / Manrope+Unbounded など各社バラバラ）。
一致するのは書体名ではなく**構造**。

### 根拠：「欧文と和文で別フォントを当てる」構造は6サイト中5サイトで確認できた

`reference-sites.json` の `font_family` を見ると、和文サイトはいずれも欧文用フォントと
和文用フォントを別に指定している。

| サイト | 欧文 | 和文 |
|---|---|---|
| ds-k | Barlow | heisei-kaku-gothic-std, Yu Gothic, 游ゴシック 他 |
| komeinc | neue-haas-unica / freightbigcmp-pro | （英語主体サイトのため和文指定は本文中に確認できず） |
| arkreis | aktiv-grotesk, termina | Hiragino Kaku Gothic ProN, Hiragino Sans, Meiryo 他 |
| zeroten | Manrope, Unbounded | Noto Sans JP |
| 109ichiki | var(--font-ibm) | var(--font-ja)（変数名から和文と推定） |
| unium | 確認できず（`font_family` が空 `{}` で抽出できていない。フレームワーク側で指定されている可能性があり、このJSONからは判断不可） |

→ 「欧文はジオメトリック/グロテスク系サンセリフ、和文はゴシック体」という組み合わせ自体は
このサイトの構造（Inter + Zen Kaku Gothic New）と一致する。**フォント名の変更は不要**、
現状の組み合わせ方針を継続してよいという裏付けとして扱う。

## 2. ウェイトの使い分け

### 実測（`style.css` 内の `font-weight` 出現、全27箇所）

| ウェイト | 出現数 | 主な用途（コード上の文脈） |
|---|---|---|
| 200 | 3 | ヒーロー等の巨大見出し（clamp指定の大サイズ文字） |
| 300 | 7 | 本文（body既定）、中見出し |
| 400 | 4 | 通常テキスト |
| 500 | 11 | ラベル・ナビ・キャプションなど小さい文字 |
| 700 | 0（Google Fontsでは読み込み済みだが `style.css` 内では未使用） | — |

→ **700は現状「読み込んでいるだけで使っていない」**。今回はCSSを変更しないため直さないが、
2本目以降でフォント転送量を減らすなら `Inter:wght@200;300;400;500` に絞る選択肢がある、
という申し送り事項として `_log_01.md` に記載した。

### 外部デザインシステムとの照合

- **Ant Design**（`ant.txt` 154行目）：「ほとんどの場合 regular(400) と medium(500) で十分。
  英字の強調のみ semibold(600) を使う」
- **IBM Carbon**（`carbon.txt` 135-137行目）：「Light・Regular・SemiBoldの3段階を推奨。
  Semiboldは見出し向けで、長文には使わない」

→ どちらも「本文は400〜500、強調は1段階だけ太くする」という考え方で一致している。
このサイトの実測（本文300、ラベル500、大見出しほど軽くする200）は方向性としては近いが、
**強調に「太く」ではなく「大きく・軽く」を使っている**点が外部ドキュメントとは逆。
これは白ベース・細字を基調とするこのサイトの既定方針（`style.css` 冒頭コメント）に基づく
意図的な差なので、**このサイト独自のルールとして明文化する**：

> **見出しの強調は「太さを上げる」のではなく「サイズを上げてウェイトを下げる（500→300→200）」で作る。
> 700は本文中では使わない。将来どうしても強い強調が要る場合（警告文字など）に限り700の使用を検討する。**

## 3. サイズスケール

デジタル庁デザインシステム（`digitalgo.txt` 92行目）：「本文やUIにおいては16 CSS px以上が基準値」。
このサイトの本文は `font-size: 1rem`（16px、`style.css` 79行目）で、この基準を満たしている。**変更不要。**

Ant Design（`ant.txt` 153行目）：「フォントスケールは3〜5種類程度に抑えるべき」。

### 現状の課題：`clamp()` が9種類に分散している

`style.css` を実測すると、`font-size: clamp(...)` が次の9パターンで使われており、
値が近いのに微妙に揃っていない（狙った設計ではなく積み上げの結果と見られる）。

```
clamp(2.8rem, 8vw, 6rem)      190行目  ヒーロー見出し（トップ）
clamp(2.8rem, 7vw, 6.5rem)    314行目  ヒーロー見出し（作品詳細）
clamp(1.4rem, 5vw, 3.4rem)    610行目
clamp(2rem,   5vw, 3.4rem)    700行目
clamp(1.25rem,2vw, 1.6rem)    512行目
clamp(1.15rem,2vw, 1.5rem)    823行目
clamp(1.05rem,2vw, 1.45rem)   970行目
clamp(1.05rem,1.6vw,1.3rem)   574行目
clamp(0.95rem,1.4vw,1.1rem)   324行目
```

### このサイトのスケール（6段階に整理）

Ant Designの「3〜5種」を目安にしつつ、既存の実測値を潰さず**最も代表的な値へ寄せる形**で
6トークンに整理する。新しい数値は作らず、既存コードにある値だけを使う。

| トークン | 値 | 元にした行 | 用途の目安 |
|---|---|---|---|
| `--fs-display` | `clamp(2.8rem, 8vw, 6rem)` | 190行目 | ページ内で最も大きい見出し（1箇所限定） |
| `--fs-h1` | `clamp(2rem, 5vw, 3.4rem)` | 700行目（610行目の`1.4rem`始まりは要注意の外れ値） | セクション大見出し |
| `--fs-lead` | `clamp(1.25rem, 2vw, 1.6rem)` | 512行目 | リード文・サブコピー |
| `--fs-body-lg` | `clamp(1.15rem, 2vw, 1.5rem)` | 823行目（970行目の`1.05rem/1.45rem`はこれに統合） | 本文よりやや大きい説明文 |
| `--fs-body-sm` | `clamp(1.05rem, 1.6vw, 1.3rem)` | 574行目 | 補足テキスト |
| `--fs-label` | `clamp(0.95rem, 1.4vw, 1.1rem)` | 324行目 | 極小ラベル・メタ情報 |

※ 610行目の `clamp(1.4rem, 5vw, 3.4rem)` は最大値が `--fs-h1` と同じなのに最小値だけ
`1.4rem` と低く、意図的な差か作業中のブレか `style.css` の記述だけでは判別できない。
**確認できず**。2本目でコンテキスト（何の見出しか）を見て判断すること。

今回は `style.css` を書き換えないため、上表は「次にトークン化するときの正解」として記録するのみ。

## 4. 行間（line-height）

実測（`style.css`、13箇所）：本文系は 1.4〜1.9 に分布し、`1.75`・`1.7`・`1.8` が多数派。
見出し系は `1`・`1.15` と詰まっている。

参考サイトとの一致：
- **ds-k**：`line-height: 1.8` が82回で本文の主流、`line-height: 1` が222回で見出し・ラベル系の主流。
- **zeroten**：`line-height: 1.6` が64回で最頻値。
- **デジタル庁**（`digitalgo.txt` 111-113行目）：「一般的なウェブサイトの本文で使用される行間」として
  160%・170%を明記し、150%を「本文の行間としては最低限度」としている。

→ このサイトの本文 `line-height: 1.75`（`style.css` 81行目）は、ds-k実測（1.8）と
デジタル庁の推奨帯（1.6〜1.75）の両方に収まっており、**このまま採用を継続する**。

**このサイトのルール：**

| 用途 | line-height |
|---|---|
| 本文（和文混じり） | `1.75` |
| 大見出し（`--fs-display` 相当） | `1` 〜 `1.15` |
| 中見出し | `1.4` |
| 小さいラベル・キャプション | `1.4`〜`1.7`（既存の523・574行目付近の値を踏襲） |

## 5. 字送り（letter-spacing）

実測（`style.css`、21箇所）：`0.08em` が9回で最頻値、次に負の値（-0.01em 〜 -0.05em）が
見出し系に、`0.04em` と `0.06em` が本文・ラベル系に使われている。

### 根拠1：和文本文の正の字送り

**zeroten**：`letter-spacing: .04em` が93回で最頻値（サイト全体のほぼ唯一のパターン）。
このサイトの本文 `letter-spacing: 0.04em`（`style.css` 83行目）と完全一致。**継続。**

### 根拠2：ラベル・小文字の広め字送り

**ds-k**：`letter-spacing: .08em` が244回で圧倒的最頻値（英字ラベル・ナビ的な要素に多いと推定）。
このサイトのラベル・ナビ系（`0.08em`、9箇所）と完全一致。**継続。**

### 根拠3：大見出しほど字を詰める

**arkreis**：`letter-spacing` が `-.01em` から `-.11em` まで12段階あり、値が並んでいることから
「文字サイズが大きくなるほど負の値を大きくする（字を詰める）」運用と推定できる
（このJSONは出現回数のみで対応する font-size は分からないため、対応関係自体は**確認できず**、
値の並び方からの推定にとどまる）。
**komeinc**：`letter-spacing: -0.02em` が102回で最頻値（本文よりやや大きい文字に使われていると推定）。

→ このサイトも見出し系だけ負の字送り（`style.css` の `h1,h2,h3` で `-0.02em`、
190〜992行目付近で `-0.01em`〜`-0.05em`）になっており、傾向としては一致する。
**「見出しが大きいほど負の字送りを強める」というルールとして明文化する：**

| サイズ帯 | letter-spacing |
|---|---|
| `--fs-display` | `-0.04em`〜`-0.05em` |
| `--fs-h1` | `-0.02em`〜`-0.03em` |
| 本文サイズ以下の見出し | `-0.01em` |
| 和文本文 | `+0.04em` |
| 英字ラベル・ナビ | `+0.06em`〜`+0.08em` |

## 6. 和欧混植

`--font: 'Inter', 'Zen Kaku Gothic New', sans-serif;` の1本で欧文・和文を自動的に出し分ける方式は
`style.css` 46-47行目のコメント通りで変更なし。デジタル庁のドキュメント（`digitalgo.txt` 38-39行目）も
「OSやデバイスネイティブのシステムフォント使用を制限するものではない」「表示フォントはユーザーエージェントに
依存する前提を持つ」としており、複数フォントを優先順位で並べる現状の書き方と矛盾しない。
