# 02. 余白・レイアウト

根拠は `research/data/reference-sites.json` の `breakpoints` / `grid_template_columns` / `spacing_px`
と `research/data/design-systems/carbon_space.txt`（IBM Carbon スペーシング）。数値はすべて実測。

---

## 1. 余白の刻み

### 実測：`style.css` 内の `padding` / `margin` / `gap` の数値（px換算、117箇所）

```
2, 4×2, 6, 8×2, 9, 10×4, 12×3, 14×3, 16×2, 18×3, 20×2,
24×10, 28×5, 32×6, 36×3, 40×10, 44, 48×6, 56×5, 64×3,
72×2, 80×3, 88, 96×2, 120×3, 140×2
```

大部分が **4の倍数**（さらに大きな値は8の倍数）に収まっている。例外は `2px`（371行目、下線の
太さ調整）、`6px`（546行目、微調整）、`9px`（722行目、ボタンのpadding）、`44px`（1090行目、
768px以下のレスポンシブ調整）、`88px`（412行目、`gap`のロー方向）の5箇所のみ。

> **【学習②での訂正】** 上記の「例外は5箇所のみ」という記述は不正確だった。学習②で
> `padding` / `margin` / `gap` の全出現を数え直したところ、`2px`・`6px`・`9px` に加えて
> `10px`（4箇所）・`14px`（3箇所）が4の倍数ではなく、さらに `20px`・`28px`（5箇所）・
> `36px`（3箇所）・`72px`（3箇所） は4の倍数ではあるが下記10段階スケールのどれにも
> 乗っていない。「4の倍数かどうか」と「10段階スケールに乗っているかどうか」を混同していたのが
> 原因。正しい一覧と行番号は `04_gap-analysis.md` 第4章を参照。

### 外部デザインシステムとの照合：IBM Carbon スペーシングスケール

`carbon_space.txt` 44-86行目：「Carbonのスペーシングスケールは2・4・8の倍数を使う」
「小さい刻みと大きい刻みの両方を持つ」とあり、実際のトークンは
`spacing-01=2px, 02=4px, 03=8px, 04=12px, 05=16px, 06=24px, 07=32px, 08=40px,
09=48px, 10=64px, 11=80px, 12=96px, 13=160px` という等比に近いカーブになっている
（同ファイル57-86行目）。

→ このサイトの実測値の分布（4刻み→8刻み→2桁の大きな刻み）は、Carbonの「小さいものは細かく、
大きいものは粗く」という設計原則と方向性が一致する。**このサイトの正式な刻みとして、
実測にある値だけを採用し、次の10段階を「今後使ってよい値」として固定する：**

| トークン名 | 値 | Carbonの近い段（参考） |
|---|---|---|
| `--sp-1` | 4px | spacing-02 (4px) |
| `--sp-2` | 8px | spacing-03 (8px) |
| `--sp-3` | 12px | spacing-04 (12px) |
| `--sp-4` | 16px | spacing-05 (16px) |
| `--sp-5` | 24px | spacing-06 (24px) |
| `--sp-6` | 32px | spacing-07 (32px) |
| `--sp-7` | 40px | spacing-08 (40px) |
| `--sp-8` | 48px | spacing-09 (48px) |
| `--sp-9` | 64px | spacing-10 (64px) |
| `--sp-10` | 80px | spacing-11 (80px) |

`96px` `120px` `140px` はセクション単位の大きな余白として別枠（下記2章）。
`2px / 6px / 9px / 44px / 88px` は上記10段階のどれにも当たらない一点物の値。
削除・統合すべきかは今回判断しない（CSS変更禁止のため）。**申し送り事項として記録する。**

## 2. セクション間・コンテナ

- セクション間の余白：`padding: 140px 0`（`style.css` 141行目）。768px以下では `96px`
  （1080行目）。140と96はどちらも上記の10段階には無い「セクション専用の大きな余白」であり、
  意図的にセクション用の別スケールとして扱われていると判断できる（`.section` にしか
  使われていないため）。**このまま独立トークンとして扱ってよい。**
- コンテナ余白：`padding: 0 40px`（129-132行目）、1600px以上で `56px`、768px以下で `24px`。

### 外部デザインシステムとの照合

`carbon_space.txt` 155-157行目：「スケール外の値への逸脱は可能な限り避けるべきだが、
例外は常にある」。166-171行目：「ブレークポイントごとにスペーシングの段を1〜2段階
落とすことは許容される」（1440pxで`spacing-05`、768pxで`spacing-03`に切り替える例）。

→ このサイトの「デスクトップ140px→タブレット以下96px」「コンテナ余白 56px→40px→24px」という
ブレークポイントごとの縮小は、Carbonが明示的に許容しているパターンと一致する。**変更不要。**

## 3. グリッド

実測（`reference-sites.json` の `grid_template_columns`）：

- **109ichiki**：`repeat(var(--grid-columns),1fr)` が7回で最多。CSS変数でカラム数を可変にしている。
- **unium**：`repeat(8, 1fr)` 11回、`repeat(20, 1fr)` 7回。8分割・20分割という細かいグリッドを併用。
- **zeroten**：`subgrid` を4回使用。ネストしたグリッドに親のトラックを継承させている。

このサイトの `grid-template-columns` は `repeat(auto-fit, minmax(240px, 1fr))`
（582行目、Worksグリッド）や `repeat(auto-fit, minmax(170px, 1fr))`（860行目）など、
**カラム数を固定せず `auto-fit` + `minmax` で可変にする方式**を採用している。

→ 参考サイトの「カラム数を変数化する」（109ichiki）「用途別に複数のグリッド分割を持つ」
（unium）という発想と、このサイトの `auto-fit` 方式は目的（固定カラム数を避けて柔軟にする）が
共通している。実装方法自体は異なるが矛盾しないため、**現状の `auto-fit` 方式を継続する。**

`subgrid`（zeroten）は現状このサイトでは未使用。用途（親のグリッド線をネストした要素に
継承させる）が今のレイアウトで必要になった際の選択肢として記録するに留める。

## 4. ブレークポイント

### 実測（`reference-sites.json` の `breakpoints`、出現回数）

| 値 | 出現回数（サイト別） | 合計 |
|---|---|---|
| 1024px | 109ichiki 17 / ds-k 756 / unium 348 | **1121** |
| 768px | 109ichiki 112 / komeinc 86 / zeroten 1 | **199** |
| 835px / 834px | arkreis 81 / 38 | 119（iPad系の縦横） |
| 1025px | ds-k 70 | 70 |
| 576px | 109ichiki 10 | 10 |
| 1280px | 109ichiki 8 | 8 |
| 640px | zeroten 2 | 2 |
| 2531px | komeinc 1 | 1（外れ値） |
| 1300px | unium 1 | 1（外れ値） |
| 767px | komeinc 20 | 20 |

**1024pxが全サイト合計で圧倒的最多、768pxが次点**という結果になった。

### このサイトの現状

`style.css` の `@media` は `1600px`（大画面での余白拡張）・`1024px`（グリッドの1列化・余白調整）・
`768px`（コンテナ余白・セクション余白・グリッドのモバイル最適化、13-14章にまとまった調整）の
3段階（`style.css` 1043, 1052, 1073行目）。

→ 実測で最多だった **1024px** と次点の **768px** の両方をすでに主要ブレークポイントとして
採用できている。**変更不要。追加のブレークポイントも今のところ不要と判断する。**

`1600px`（大画面）は参考6サイトのデータには存在しない値だが、参考サイトの実測は
「スマホ〜デスクトップの縮小方向」の分岐点の集計であり、「デスクトップの中でさらに広い画面」向けの
余白拡張は別の目的（読みやすい行長を保つための余白調整）。**目的が異なるため比較対象にならない
＝現状維持でよい。**
